## Systemic Pattern Analysis: Why This System Keeps Getting Stuck

### The Recurring Loop (May 8 → May 16)

Across 31 plans and 102 commits in 8 days, the Pine autoresearch system has been through at least **4 distinct stuck-and-fix cycles**:

| Period | Root Cause | Fix Applied | Outcome |
|--------|-----------|-------------|---------|
| May 8-9 | Duplicate sweeps, scheduler stuck | Guards, hardening | Unblocked temporarily |
| May 10-11 | Tabu saturation (22-candidate pool exhausted) | Age-bound tabu, stagnation escalation | Unblocked, but pool still small |
| May 12-13 | 0-variant crash, stagnation never escalates, similarity rotation noise | Low-emission escalation, similarity guard, tabu exhaustion signal | Unblocked, but escape still gated on `generatedLanesExhausted` |
| May 14-15 | Track families advertised but not generating, regime diagnostics dishonest | Real patch pools, family generation, regime row alignment | Unblocked, but tabu re-stamps and escape eligibility still broken |
| May 15-16 (current) | Tabu age re-stamping, zero-emission deadlock, escape not eligible, track not rotating | **This plan** | Pending |

### The Structural Problem

Each fix addresses the immediate symptom but leaves the deeper structural issue intact:

1. **The tabu system is fundamentally fragile.** It was designed for a small pool (22 candidates) with short cycles. Now with expanded families (10+ families, hundreds of possible patches), the tabu system's string-based bootstrap, single-cycle stamping, and lack of per-cycle caps create cascading failures at scale.

2. **Escape eligibility is too narrow.** `decideStagnationEscapePlan` requires `generatedLanesExhausted` (both `globalAllParameter` AND `exitRegime` lanes), which is a condition that rarely fires in the track-based research mode. The system can be completely stuck (zero emission, all tabu) without meeting this condition.

3. **The `noNewCandidateStreak` counter is unreliable as the sole escape trigger.** When the system emits even one variant (which then fails gates), the streak resets. This means `escapeActive` in `buildTrackCandidateBatch` can be `false` even at `stagnationLevel: 3`.

4. **Config drift accumulates.** `tabuBootstrapManifestLimit: 200` was set when the system had few manifests. Now it replays 200 manifests worth of fingerprints into the tabu set every cycle, overwhelming the 40-entry cap that was intended to keep the set manageable.

### Why This Plan Should Break the Loop

This plan is the first to address ALL THREE layers simultaneously:
- **Tabu layer:** Age preservation + same-cycle flood cap + policy resolution fix
- **Escape layer:** Zero-emission eligibility + stagnation-triggered fallback
- **Rotation layer:** Zero-emission track rotation + config alignment

Previous plans fixed one layer at a time, which allowed the other layers to re-create the stuck condition.

### Task 6: Attach Stable Patch Fingerprints to Track and Fallback Variants — VALIDATED WITH DEPENDENCY NOTE

**Bug confirmation:** `buildMetadata` (line 94 in `pine-track-generators.mjs`) currently returns:
```js

```

No `patchFingerprint` or `patchFingerprintVersion` field. The plan's evidence item #6 states: "`searchPlan.variants[*].patchFingerprint` is often `null`, weakening novelty evidence and post-run auditability." This is because the field is never set at the source.

- `scripts/lib/pine-global-search.mjs` EXISTS and exports `buildChampionConfigFingerprint` (line 128)

Both imports the plan requires are available.

**Plan's approach is correct but has a subtlety:**

The plan's `buildMetadata` modification computes `championConfigFingerprint` from the config with patch keys removed:
```js
const championConfigFingerprint = buildChampionConfigFingerprint(
  config ? { ...config, ...Object.fromEntries(patchKeys.map((key) => [key, undefined])) } : {}
);
```

This is wrong — it tries to reconstruct the "base before patch" by setting patch keys to `undefined`. But `buildChampionConfigFingerprint` calls `buildCanonicalConfigFingerprint` which does `JSON.stringify(stableValue(stripConfigIdentity(config)))`. Keys with `undefined` values are dropped by `JSON.stringify`, so this effectively removes the patched keys from the fingerprint. This gives the champion's fingerprint WITHOUT those keys, which is NOT the same as the champion's fingerprint WITH the original values.

**The correct approach** (which the plan's implementation note acknowledges): pass the `base` config (champion config before mutation) into `buildMetadata` and compute `championConfigFingerprint` from that. The plan says: "if the exact champion-before-patch config is needed... change the caller to pass `base` into `buildMetadata({ baseConfig: base, ... })`."

The implementer should use the second approach:
```js
const patchFingerprint = buildLanePatchFingerprint({
  championConfigFingerprint: buildChampionConfigFingerprint(baseConfig || config),
  lane,
  mutationFamily: family,
  patch,
});
```

Where `baseConfig` is the incumbent config passed through from `buildTrackCandidateBatch`.

**Caveats for implementer:**

1. **The plan's code shows `buildMetadata` returning BOTH top-level fields AND a nested `metadata` object.** This is intentional — the variant object gets `patchFingerprint` and `patchFingerprintVersion` at the top level (for tabu/novelty checks) AND inside `metadata` (for manifest serialization). The implementer must ensure both are set.

2. **The test asserts `variant.patchFingerprint.length >= 32`.** `buildLanePatchFingerprint` returns a sha256 hex string (64 chars). This assertion is safe.

3. **The test asserts `variant.metadata.patchFingerprint` exists.** The plan's `buildMetadata` must include `patchFingerprint` in the returned `metadata` object.

4. **Existing tests won't break** because they don't assert the ABSENCE of `patchFingerprint`. They check other fields. Adding new fields to the return object is additive.

**Verdict:** Task 6 is sound but the implementer should use `baseConfig` (the incumbent) for fingerprint computation rather than the `undefined`-key hack. The plan's implementation note already flags this.

## Hidden Risks Not Addressed by the Plan

### Risk 1: `tabuBootstrapManifestLimit` reduction may cause tabu amnesia

Reducing from 200 → 48 means the system only looks at the last 48 manifests for rejected fingerprints. If a candidate was rejected 49+ cycles ago, it won't be in the tabu set and could be re-tested. This is actually DESIRABLE at high stagnation (re-testing old candidates with new escape parameters), but at low stagnation it could waste cycles re-evaluating known-bad candidates.

**Mitigation:** The `maxAgeCycles: 20` policy already prunes entries older than 20 cycles. With 48 manifests bootstrapped, entries from cycles 20+ ago would be pruned anyway. So the reduction from 200 → 48 only matters for entries between age 20 and 48 — which are already pruned by the age policy. **Net effect: minimal.** The real benefit is reduced I/O (reading 48 files instead of 200).

### Risk 2: `stagnationLevel >= 1` escape activation may be too aggressive

After Task 4, ANY stagnation (level 1+) activates fallback generation. Level 1 can fire after just 2-3 cycles of low emission. This means the system starts generating cross-family fallback variants very early, before the current track has been properly explored.

**Mitigation:** The fallback variants are ADDED to the track variants, not replacing them. The track still generates its own candidates first. Fallback variants only fill remaining budget slots. At level 1, the temperature boost is lower (`temperatureBoost: 1.5` vs `stagnationTemperatureBoost: 4` at level 2+), so fallback variants are conservative. This is acceptable.

### Risk 3: Zero-emission rotation with `zeroEmissionRotateAfter: 1` may thrash between tracks

If ALL tracks are exhausted (all produce zero emission), the system will rotate every cycle without making progress. Each rotation resets `sameTrackCycleStreak` but doesn't solve the underlying tabu saturation.

**Mitigation:** Tasks 1-2 (tabu age preservation + flood cap) should prevent total tabu saturation. Task 4 (stagnation fallback) provides fresh candidates from other families. If all of these fail simultaneously, the system is genuinely converged and should declare convergence (Phase 3.1 from the May 14 comprehensive plan — not yet implemented). The rotation at least prevents one track from monopolizing cycles while stuck.

### Risk 4: `context-exit-shaping` family may not have patch pools

The plan adds `context-exit-shaping` to `stagnationFallbackFamilies` but this family may not have a corresponding patch pool in `pine-track-generators.mjs`. If `getPatchPool('context-exit-shaping', base)` returns `undefined` or `[]`, the family contributes nothing to fallback generation.

**Mitigation:** The implementer should verify that `context-exit-shaping` has a patch pool. If not, either add one or remove it from the config. The plan's test (Task 4 Step 1) asserts that specific families emit candidates — if `context-exit-shaping` is in the assertion list and has no pool, the test will fail and catch this.

### Risk 5: `decideMatrixPromotion` `gateDiagnostics` may not propagate to manifest

Task 7 adds `gateDiagnostics` to the return of `decideMatrixPromotion`, but the manifest serialization code must also include it. If `buildScoutOrchestrationState()` or the manifest writer doesn't spread the full `matrixDecision` object into the manifest, the diagnostics won't appear in the final artifact.

**Mitigation:** The plan acknowledges this: "If `decideMatrixPromotion()` does not receive both champion/challenger in that exact scope, build the same object in `buildScoutOrchestrationState()` after `matrixDecision` and merge it into manifest-local `matrixDecision`." The implementer must trace the data flow from `decideMatrixPromotion` return → manifest serialization to ensure `gateDiagnostics` survives.

## Task 11: Convergence Declaration Hardening (New Addition)

### Discovery: Convergence Mechanism Already Exists

The codebase already has a convergence declaration system:

1. **Accumulation** (`pine-autoresearch-tracks.mjs:562-574`): `nextTrackState` increments `noScoreImprovementStreak` each cycle where no score improvement occurs, resets on rotation or improvement.
2. **Declaration** (`pine-autoresearch.mjs:3476-3491`): When streak reaches `noScoreImprovementConvergeAfter` (default fallback: 4), writes `converged.json` with champion details.
3. **Enforcement** (`pine-autoresearch.mjs:2948-2960`): On next cycle start, reads the marker and short-circuits with `{ skipped: true, reason: 'converged' }`. Bypassed by `config.forceCycle`.

### Problems With the Current Implementation

1. **`noScoreImprovementConvergeAfter` is not in the default config.** It falls back to `4` via `config.rotationPolicy?.stagnation?.noScoreImprovementConvergeAfter ?? 4`. This means the system converges after just 4 cycles of no score improvement — which is too aggressive given that Tasks 1-5 are designed to RECOVER from stagnation. The system would declare convergence before the recovery mechanisms have time to work.

2. **Convergence fires on `noScoreImprovementStreak` alone, ignoring escape state.** If the system is at stagnation level 3 with active escape (progressive-widen), it should NOT converge — it should keep trying with widened parameters. Convergence should only fire when escape mechanisms have been exhausted AND no improvement is found.

3. **No convergence reset on champion change.** If a new champion is promoted externally (manual intervention, different matrix), the `converged.json` marker persists and blocks future cycles. The marker stores `championFingerprint` but the enforcement code doesn't compare it to the current champion.

4. **The convergence marker doesn't account for the fixes in this plan.** After Tasks 1-5, the system has new recovery paths (zero-emission escape, stagnation fallback, track rotation). Convergence should only fire after these paths have been tried and failed.

  noScoreImprovementStreak = 0,
  stagnationLevel = 0,
  stagnationEscape = {},
  allTracksExhausted = false,
  policy = {},
} = {}) {
  const threshold = Math.max(1, Number(policy.noScoreImprovementConvergeAfter) || 6);
  const requireEscapeExhaustion = policy.requireEscapeExhaustion !== false;

  if (noScoreImprovementStreak < threshold) return false;

    if (stagnationEscape?.mode && stagnationEscape.mode !== 'none') return false;
    // Don't converge until stagnation has reached max level
    const maxLevel = Number(policy.maxStagnationLevel) || 4;
    if (stagnationLevel < maxLevel) return false;
  }

  return true;
}
